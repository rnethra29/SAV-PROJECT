# Database layer

- **`migrations/`** — canonical, ordered, applied by `npm run migrate` (see `migrate.js`). This is the single source of truth for schema, functions, triggers and views. Files are idempotent (`IF NOT EXISTS` / `CREATE OR REPLACE` / duplicate-object-safe `DO $$` blocks, `ADD VALUE IF NOT EXISTS` for ENUMs) so re-running is always safe.
  - `001`–`011`: Commercial Lifecycle module (`com_*`).
  - `012`–`019`: **Sites module → Client Management submodule** (`clm_client*`/`clm_payment*`). `012` also `ALTER TYPE`-extends `com_document_entity_type`/`com_approval_entity_type` with the new Client/ClientContact/ClientRequirement/ClientInvoice/ClientPayment values — Documents and Approvals are reused from Commercial Lifecycle, not duplicated (see `SAV_ERP_Client_Management_Module_Architecture.md` §2/§9/§16).
  - `020`–`030`: **Sites module → Vendor Management & Procurement submodule** (`vnd_*`, plus the `clm_project`/`clm_project_cost`/`clm_project_expense` extension to Client Management, plus RBAC `sec_*`). `020` further extends `com_document_entity_type`/`com_approval_entity_type` (+6/+3 values) and `com_audit_action` (+7 values), and adds `expiry_date`/`verification_status` columns to `com_documents` (see `SAV_ERP_Sites_Vendor_Procurement_Module_Architecture.md` §0/§8/§11/§12).
- **`functions/`**, **`views/`**, **`schema/`** — kept as thin pointers (below) rather than duplicated copies of the SQL in `migrations/`, to avoid the two drifting apart. Open the referenced migration file directly to read/edit the actual definition.
  - Helper functions & triggers → `migrations/002_helper_functions.sql`, `migrations/008_boq_tables.sql` (word-count trigger), `migrations/017_clm_payment_tables.sql` (client-side allocation-sum guard trigger), `migrations/024_vnd_purchase_order_tables.sql` (PO header-total recalc trigger), `migrations/026_vnd_vendor_payment_tables.sql` (vendor-side allocation-sum guard trigger)
  - Views → `migrations/011_views.sql` (`v_estimation_item_cost`, `v_item_commercial_analysis`, `v_item_commercial_analysis_final`), `migrations/019_clm_views.sql` (11 Client 360°/billing/cost views), `migrations/030_vnd_clm_views.sql` (6 vendor-performance/project-financial views)
  - Full table DDL → `migrations/003_*.sql` through `010_*.sql` (Commercial Lifecycle), `013_*.sql` through `018_*.sql` (Client Management), `021_*.sql` through `029_*.sql` (Vendor Management & Procurement + RBAC)
- **`seeds/`** — static seed data applied by `npm run seed` (see `seed.js`): `001_lookup_data.js` (Commercial Lifecycle lookups), `002_client_management_lookup_data.js` (`clm_client_type`, `clm_industry`, `clm_contact_type`), `003_vendor_procurement_lookup_data.js` (`vnd_vendor_type`, `vnd_material_category`), `004_rbac_seed_data.js` (10 `sec_role` rows, a representative `sec_permission` set, and the `sec_role_permission` grants between them).

## Setup

1. Fill in `.env` (see `.env.example`) with your Supabase project's `DATABASE_URL` (direct/session Postgres connection string), `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `SUPABASE_JWT_SECRET`.
2. `npm run migrate` — creates every enum/table/index/function/trigger/view for all three modules.
3. `npm run seed` — populates every lookup table plus baseline RBAC (requires at least one row in the external `users` table, or set `SEED_USER_ID`).

External master tables (`companies`, `branches`, `users`, `employees`, `clients`, `projects`, `sites`, `currencies`, `taxes`) are **not** created by these migrations — they belong to other SAV ERP modules and are referenced by FK only, per each module's architecture spec. (`vendors` *is* now created here, as `vnd_vendor` — see below.) Two FK-target reconciliations are still open, both flagged in-line in the relevant migration file's header comment:
- `clm_client` (Client Management) vs. the external `clients` table `com_rfq`/`com_boq` FK to — see the escalation notes at the top of `SAV_ERP_Client_Management_Module_Architecture.md`.
- `clm_project` (Vendor Management & Procurement) vs. the external `projects` table `com_rfq`/`com_boq`/`com_po` FK to — see `022_clm_project_tables.sql`'s header comment and `SAV_ERP_Sites_Vendor_Procurement_Module_Architecture.md` §0.
